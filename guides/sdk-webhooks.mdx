Fused webhook receivers let your code react to events from any service in your SDK — Jira issue created, GitHub member added, Stripe payment completed — without exposing a public HTTP endpoint. Instead of registering an inbound webhook URL that your infrastructure must serve, Fused provisions a receiver URL and pushes events to your process over an **outbound WebSocket connection** that your code initiates.

## How Fused webhook receivers work

Traditional webhooks require a public HTTPS endpoint. Fused inverts the model: your process connects outbound to Fused's infrastructure, and Fused streams typed events down that connection as they arrive. Because the connection is outbound, your code works identically on:

- A developer laptop with no public IP
- A serverless function with an ephemeral address
- A container inside a private VPC
- A CI runner or ephemeral test environment

Fused provisions one dedicated receiver URL per service, visible in the dashboard under your SDK's **Webhooks** tab.

## Register a receiver

Import `fusedWebhooks` from your generated SDK and call `registerReceiver` with a receiver name and your Fused API key:

```typescript
import {
  FusedSDK as OnboardingSDK,
  fusedWebhooks
} from "@acme/onboarding-sdk";

const sdk = new OnboardingSDK({
  github: { token: "ghp_..." },
  slack: { token: "xoxb_..." }
});

const receiver = fusedWebhooks.registerReceiver("onboarding", "fused_api_key");
```

The receiver name identifies this connection in the Fused dashboard and in trace logs. Use a name that reflects the workflow or service consuming the events.

<Note>
  `registerReceiver` establishes the outbound WebSocket connection immediately. Keep the process alive for the connection to remain open. In serverless environments, consider using a long-running worker process or a persistent container for webhook receivers.
</Note>

## Listen for events

Attach handlers to the receiver using `.on()`. The first argument is a typed event enum value from the generated SDK; the second is an async handler that receives a fully typed event object:

```typescript
import {
  FusedSDK as OnboardingSDK,
  fusedWebhooks,
  JiraWebhook,
  GithubWebhook
} from "@acme/onboarding-sdk";

const sdk = new OnboardingSDK({
  github: { token: "ghp_..." },
  slack: { token: "xoxb_..." }
});

const receiver = fusedWebhooks.registerReceiver("onboarding", "fused_api_key");

receiver.on(JiraWebhook.ISSUE_CREATED, async (event) => {
  const { issue } = event.body;
  if (issue.fields.project.key !== "ONBOARD") return;

  await sdk.github.repos.addCollaborator({
    owner: "acme-corp",
    repo: "platform",
    username: issue.fields.assignee.accountId,
    permission: "push"
  });
});

receiver.on(GithubWebhook.MEMBER_ADDED, async (event) => {
  const { member, repository } = event.body;

  await sdk.slack.chat.postMessage({
    channel: "#engineering",
    text: `👋 ${member.login} now has access to ${repository.name}. Welcome!`
  });
});
```

This example builds a fully event-driven onboarding workflow:

1. **`JiraWebhook.ISSUE_CREATED`** fires when a new Jira issue is created. If it belongs to the `ONBOARD` project, the handler immediately grants the assignee repository access on GitHub.
2. **`GithubWebhook.MEMBER_ADDED`** fires when GitHub confirms the collaborator was added. The handler posts a welcome message to the `#engineering` Slack channel.

No polling, no cron jobs, no public endpoints.

## Generated event enums and typed payloads

For every service in your SDK that supports webhooks, Fused generates:

- **An event enum** (e.g., `JiraWebhook`, `GithubWebhook`) listing every subscribable event type
- **A typed payload interface** for each event — `event.body` is fully typed, so your IDE autocompletes field names and TypeScript catches typos at compile time

```typescript
receiver.on(JiraWebhook.ISSUE_UPDATED, async (event) => {
  // event.body is typed as JiraIssueUpdatedPayload
  const { issue, changelog } = event.body;
  console.log(issue.key, changelog.items);
});
```

<Tip>
  Check the generated `webhooks/` directory in your SDK package for the full list of event enums and payload types for each service you bundled.
</Tip>

## Where webhook receivers work

Because receivers use outbound connections, they work in environments where inbound HTTP is unavailable or impractical:

| Environment | Works? | Notes |
|---|---|---|
| Local development | ✅ | No tunnel (ngrok, etc.) needed |
| AWS Lambda / Vercel Functions | ⚠️ | Use a persistent worker process — short-lived functions will drop the connection |
| Long-running containers (ECS, Kubernetes) | ✅ | Ideal — connection stays open for the container's lifetime |
| Private VPC / corporate network | ✅ | Outbound HTTPS and WebSocket must be permitted |
| Ephemeral CI runners | ✅ | Useful for integration tests that react to real webhook events |

<Warning>
  Serverless functions that exit after each invocation are not suitable as webhook receiver hosts. The WebSocket connection closes when the process exits. Use a persistent worker process or a long-running container to host receivers in production.
</Warning>

## Production setup

In production, read credentials from environment variables and keep the receiver process running for the lifetime of your service. A minimal production entry point looks like this:

```typescript
import {
  FusedSDK as OnboardingSDK,
  fusedWebhooks,
  JiraWebhook,
  GithubWebhook
} from "@acme/onboarding-sdk";

const sdk = new OnboardingSDK({
  github: { token: process.env.GITHUB_TOKEN! },
  slack: { token: process.env.SLACK_TOKEN! }
});

const receiver = fusedWebhooks.registerReceiver("onboarding", process.env.FUSED_API_KEY!);

// Attach all event handlers before the process idles
receiver.on(JiraWebhook.ISSUE_CREATED, async (event) => {
  const { issue } = event.body;
  if (issue.fields.project.key !== "ONBOARD") return;
  await sdk.github.repos.addCollaborator({
    owner: "acme-corp",
    repo: "platform",
    username: issue.fields.assignee.accountId,
    permission: "push"
  });
});

receiver.on(GithubWebhook.MEMBER_ADDED, async (event) => {
  const { member, repository } = event.body;
  await sdk.slack.chat.postMessage({
    channel: "#engineering",
    text: `👋 ${member.login} now has access to ${repository.name}. Welcome!`
  });
});

// Keep the process alive
process.stdin.resume();
```

Run this as a dedicated long-lived process — a Docker container, a Kubernetes Deployment, or a PM2-managed Node.js service. The receiver reconnects automatically on transient network interruptions.

<Info>
  Webhook receivers are currently supported in **TypeScript SDKs only**. Python SDK support is on the roadmap.
</Info>
