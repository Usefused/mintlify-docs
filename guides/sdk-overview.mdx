Fused generates a typed client library from the API services your team actually uses. Instead of juggling multiple third-party SDKs, writing auth boilerplate, and wiring up retries by hand, you define which endpoints you need and Fused emits a single, self-contained package — with authentication, retries, tracing, and typed errors already built in. You own the output: there is no Fused runtime dependency in the generated code.

## What a generated SDK is

A Fused SDK is a typed client library scoped to the exact endpoints your team needs. Fused reads your service definitions, filters to the operations you've selected, and generates clean TypeScript or Python source code that you install like any other package. The generated code is yours to inspect, fork, and deploy anywhere.

Every generated SDK includes:

- **Typed request and response models** — catch mistakes at compile time, not in production
- **Auth handling** — tokens, OAuth flows, and API keys are wired up in the constructor; no manual header management
- **Automatic retries** — configurable per service, with exponential backoff out of the box
- **Distributed tracing** — each request emits trace spans you can pipe to your existing observability stack
- **Typed errors** — every failure mode is a typed object you can `catch` and inspect, not an opaque `Error`

<Note>
  The generated SDK has **no vendor runtime dependency**. The output is plain TypeScript or Python source code. You can audit it, modify it, and ship it without any Fused packages installed in production.
</Note>

## Business Capability SDKs

Fused lets you bundle multiple third-party, partner, and internal APIs into a single package organized around a business domain. Instead of importing a Jira client, a GitHub client, and a Slack client separately, you ship one `OnboardingSDK` that encapsulates all three — with a single constructor call to configure credentials.

This pattern keeps service coupling explicit, makes credentials auditable in one place, and gives every engineer on your team the same typed surface area to work against.

## Generate your SDK

### From the dashboard

<Steps>
  <Step title="Open your project">
    Navigate to your project in the [Fused dashboard](https://app.usefused.com) and select **SDKs** from the sidebar.
  </Step>
  <Step title="Select services and endpoints">
    Choose the third-party, partner, or internal APIs you want to bundle. For each service, select only the endpoints your team needs — unused operations are excluded from the generated package.
  </Step>
  <Step title="Name your SDK">
    Give your SDK a package name that reflects the business domain, for example `@acme/onboarding-sdk`. This name is used in the generated `package.json` (TypeScript) or `pyproject.toml` (Python).
  </Step>
  <Step title="Generate and download">
    Click **Generate SDK**. Fused compiles the package and offers a `.zip` download. Extract the archive and install it into your project.
  </Step>
</Steps>

### From the CLI

If you prefer a code-first workflow, use `fused-cli` to generate SDKs programmatically:

<CardGroup cols={1}>
  <Card title="fused-cli: create command" icon="terminal" href="/cli/create">
    Run `fused create sdk` to scaffold a new SDK from the command line. Integrate SDK generation into your CI pipeline or local development workflow.
  </Card>
</CardGroup>

```bash
fused create sdk --services jira,github,slack --name @acme/onboarding-sdk --lang typescript
```

## Install the generated package

<Tabs>
  <Tab title="TypeScript">
    After downloading and extracting the `.zip`:

    ```bash
    cd acme-onboarding-sdk
    npm install
    ```

    Then add it to your application:

    ```bash
    npm install ../acme-onboarding-sdk
    # or publish to your private registry and install from there
    ```
  </Tab>
  <Tab title="Python">
    After downloading and extracting the `.zip`:

    ```bash
    cd acme_onboarding_sdk
    pip install -e .
    ```

    Or build a wheel and install it in any environment:

    ```bash
    pip install dist/acme_onboarding_sdk-0.1.0-py3-none-any.whl
    ```
  </Tab>
</Tabs>

## Rename FusedSDK to match your domain

The generated entry point exports a class named `FusedSDK`. Rename it at import time to reflect the business domain your SDK represents:

```typescript
import { FusedSDK as OnboardingSDK } from "@acme/onboarding-sdk";

const sdk = new OnboardingSDK({
  jira: { token: "jira_..." },
  github: { token: "ghp_..." },
  slack: { token: "xoxb_..." }
});
```

This keeps your application code readable — `sdk.jira.issues.create(...)` reads like domain logic, not vendor plumbing.
