OpenAPI is the most common way to describe a REST API, and Fused treats it as a first-class ingestion format. Whether you're working with a public SaaS API that ships a hosted spec, an internal service that generates one at build time, or a legacy Swagger file checked into source control, you can turn it into a Fused service in a few minutes. From there, Fused generates typed SDKs, MCP servers, and webhook receivers without any further manual work.

## Supported formats

Fused accepts the following OpenAPI variants:

| Format | Versions supported |
|---|---|
| OpenAPI | 3.0.x, 3.1.x |
| Swagger | 2.0 |

Both JSON and YAML encodings are supported for all variants.

## What Fused extracts

When you ingest an OpenAPI spec, Fused reads and stores:

- **Paths and operations** — every endpoint defined under `paths`, including HTTP method, path parameters, query parameters, request body, and all declared response schemas.
- **Security schemes** — API key (header or query), HTTP Bearer, HTTP Basic, OAuth 2.0 flows (authorization code, client credentials, implicit, password), and OpenID Connect.
- **Component schemas** — reusable request and response models declared under `components/schemas`, used to produce typed models in generated SDKs.
- **Webhook definitions** — paths declared under `webhooks` (OpenAPI 3.1) or equivalent `x-webhooks` extensions, used to scaffold typed webhook receivers.
- **Server metadata** — base URLs, server variables, and any `x-` extension fields Fused recognises for operational configuration.

## Ingest an OpenAPI spec

<Steps>
  <Step title="Open Services and start a new service">
    In the Fused dashboard, click **Services** in the left sidebar, then click **New service**. On the format selection screen, choose **OpenAPI**.
  </Step>
  <Step title="Provide the spec">
    You have three options:

    <CodeGroup>
    ```text Paste a URL
    https://api.example.com/openapi.json
    ```

    ```text Upload a file
    # Drag and drop or browse for your .yaml / .json / .yml file
    ```

    ```yaml Paste raw content
    openapi: "3.1.0"
    info:
      title: Example API
      version: "1.0.0"
    paths:
      /users:
        get:
          ...
    ```
    </CodeGroup>

    Fused fetches or reads the spec and displays a parse summary. If there are any validation warnings, they appear here — you can usually proceed anyway.
  </Step>
  <Step title="Select endpoints to include">
    Fused lists every operation it found, grouped by tag or path prefix. Check or uncheck individual operations, or use the **Select all** / **Deselect all** controls per group. You must include at least one operation to save the service.

    <Tip>
      Start with a focused set of endpoints. You can always add more later by editing the service — no need to re-ingest the entire spec.
    </Tip>
  </Step>
  <Step title="Configure authentication">
    Fused pre-fills the authentication method it detected from the spec's `securitySchemes`. Review the detected scheme and configure it for your consumers:

    - **API key** — confirm the header name (e.g. `X-API-Key`) or query parameter name. Fused inserts a placeholder your SDK consumers will supply at runtime.
    - **Bearer token** — confirm the `Authorization: Bearer <token>` pattern. Fused generates a constructor parameter for the token.
    - **OAuth 2.0** — select the flow (authorization code, client credentials, etc.) and provide the token endpoint URL and any required scopes. Fused generates the full OAuth exchange logic in your SDK.

    <Note>
      Credential values are never stored in the service definition. Fused stores only the authentication *scheme* (field names, flow type, URLs). Your consumers supply actual credentials at SDK initialisation time.
    </Note>
  </Step>
  <Step title="Name and save the service">
    Enter a name for the service (e.g. "Stripe Payments API") and an optional description. Click **Save service**. The service is created and appears in your Services dashboard, ready for artefact generation.
  </Step>
</Steps>

## Re-ingesting a spec

APIs change over time. To pick up new endpoints or updated schemas, open the service in the dashboard and click **Re-ingest spec**. Fused fetches the latest version of the spec and shows you a diff:

- **New operations** are highlighted in green — you can add them to the service.
- **Modified schemas** are highlighted in yellow — review the change before accepting.
- **Removed operations** are highlighted in red — Fused flags them so you can decide whether to remove them from the service and any derived artefacts.

Accepting changes does not automatically regenerate artefacts. You trigger regeneration separately so you control when breaking changes reach consumers.

## Internal APIs

If your API is internal and not publicly reachable, use one of these approaches:

- **Paste the spec directly** — copy the raw JSON or YAML and paste it into the editor. Fused parses it locally without making an outbound request.
- **Host the spec on an accessible URL** — if your CI pipeline publishes the spec to an internal URL, make sure that URL is reachable from Fused's ingestion service, or use a temporary tunnel during ingestion.

<Warning>
  Fused does not store your raw spec file after ingestion — only the extracted service definition is persisted. If you need to re-ingest, keep the original spec accessible.
</Warning>

## Troubleshooting

| Problem | What to check |
|---|---|
| "Could not fetch spec" | Confirm the URL is publicly reachable and returns a valid JSON or YAML response with the correct `Content-Type`. |
| "No operations found" | Check that your spec has a `paths` object with at least one operation. Fused also checks for `webhooks` (3.1) as a fallback. |
| "Unknown security scheme" | Fused supports `apiKey`, `http`, `oauth2`, and `openIdConnect`. Custom schemes are extracted as-is and can be configured manually. |
| Parse warnings on Swagger 2.0 | Fused converts Swagger 2.0 internally. Most specs parse cleanly; warnings usually relate to non-standard extensions. |
