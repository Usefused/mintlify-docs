Fused supports GraphQL as a first-class ingestion format. You can connect a GraphQL API by pointing Fused at a live introspection endpoint or by uploading a schema file — Fused will discover every query, mutation, and subscription the API exposes, let you select which operations to include, and turn them into typed SDK methods, MCP tools, and webhook receivers, just like any other service.

## Supported inputs

Fused accepts GraphQL schemas in two forms:

- **Introspection endpoint** — a live URL that responds to GraphQL introspection queries (i.e. `POST` with `{ __schema { ... } }`). Most GraphQL APIs enable this by default.
- **Schema file** — a `.graphql` (SDL) file or a `.json` file containing a raw introspection result. Upload either directly from your local machine.

<Tip>
  If the API you're connecting doesn't expose a formal schema and doesn't support introspection, consider exporting the collection from Postman and ingesting it as a custom service via the [Services ingestion flow](/guides/services-overview) instead.
</Tip>

## Ingest a GraphQL schema

<Steps>
  <Step title="Open Services and start a new service">
    In the Fused dashboard, click **Services** in the sidebar, then **New service**. On the format selection screen, choose **GraphQL**.
  </Step>
  <Step title="Provide the schema source">
    Choose one of the two input methods:

    <CodeGroup>
    ```text Introspection endpoint URL
    https://api.example.com/graphql
    ```

    ```graphql Upload a .graphql file
    # SDL example
    type Query {
      user(id: ID!): User
      users(limit: Int): [User!]!
    }

    type Mutation {
      createUser(input: CreateUserInput!): User
    }
    ```

    ```json Upload a .json introspection result
    {
      "__schema": {
        "queryType": { "name": "Query" },
        "types": [ ... ]
      }
    }
    ```
    </CodeGroup>

    If you provide an endpoint URL, Fused sends an introspection query to that URL immediately. The schema is fetched and parsed in the dashboard — you don't need to run any commands locally.
  </Step>
  <Step title="Add authentication headers for introspection">
    Many GraphQL APIs require authentication even for introspection. Before Fused sends the introspection query, you can add arbitrary HTTP headers:

    ```http
    Authorization: Bearer your-token-here
    X-API-Key: your-api-key-here
    ```

    Enter any required headers in the **Authentication headers** panel. These headers are used only during introspection — they are not stored as runtime credentials in the service definition.

    <Note>
      After ingestion, Fused will ask you to configure the runtime authentication scheme separately (see Step 4). The headers you enter here are only needed for Fused to read the schema.
    </Note>
  </Step>
  <Step title="Select operations to include">
    Fused displays all discovered operations in three groups:

    - **Queries** — read operations that fetch data.
    - **Mutations** — write operations that modify data.
    - **Subscriptions** — real-time event streams (where supported by the API).

    Check or uncheck individual operations to include them in your service. Each selected operation becomes a method in generated SDKs and a tool in generated MCP servers.

    <Tip>
      Fused maps each operation's arguments to typed input parameters and each operation's return type to a typed response model. The more precisely you scope your selection, the leaner your generated artefacts will be.
    </Tip>
  </Step>
  <Step title="Configure runtime authentication">
    After selecting operations, configure how consumers of your generated artefacts will authenticate at runtime. Fused supports the most common GraphQL auth patterns:

    - **Bearer token** — consumers pass a token; Fused injects `Authorization: Bearer <token>` on every request.
    - **API key header** — consumers pass a key; Fused injects it as the header name you specify.
    - **Custom header** — for any other header-based scheme, enter the header name and Fused treats it as an opaque string consumers supply.

    <Warning>
      Cookie-based authentication and session flows are not currently supported for GraphQL services. Use a token-based scheme or contact Fused support to discuss your requirements.
    </Warning>
  </Step>
  <Step title="Name and save the service">
    Enter a name for the service (e.g. "GitHub GraphQL API") and an optional description. Click **Save service**. The service is created and appears in your Services dashboard.
  </Step>
</Steps>

## How operations map to SDK methods

Each selected GraphQL operation becomes a single typed method in the generated SDK. Fused uses the operation name as the method name, camelCased to match the target language's convention. For example:

| GraphQL operation | TypeScript SDK method | Python SDK method |
|---|---|---|
| `query GetUser` | `client.getUser(...)` | `client.get_user(...)` |
| `mutation CreateIssue` | `client.createIssue(...)` | `client.create_issue(...)` |
| `subscription OnCommentAdded` | `client.onCommentAdded(...)` | `client.on_comment_added(...)` |

All input arguments defined in the operation are surfaced as typed parameters. The return type is a generated model that mirrors the GraphQL selection set you declared in the operation. Fused infers a sensible default selection set from the schema, and you can customise it after saving the service.

## Re-ingesting a schema

If the GraphQL API adds new operations or changes existing types, re-ingest the schema by opening the service in the dashboard and clicking **Re-ingest schema**. For introspection endpoints, Fused re-queries the live API. For uploaded files, you can upload a new version.

Fused shows you a diff of new, modified, and removed operations before applying any changes, so you remain in control of what lands in your artefacts.

<Info>
  Subscription operations are surfaced in the service definition but currently generate SDK methods that return an observable or async iterator depending on the target language. Full MCP streaming support for subscriptions is on the Fused roadmap.
</Info>
