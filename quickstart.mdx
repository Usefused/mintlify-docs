From nothing to one App your code and agents can use through SDK, MCP, or REST. Roughly ten minutes, most of it waiting on a browser tab.

<Note>
  This assumes you already have an Engine to talk to — hosted, or one you started yourself. If not, [get one running first](/deploy-an-engine); every command below needs it.
</Note>

## Install

```bash
curl -sSL https://raw.githubusercontent.com/Usefused/cli/main/install.sh | bash
fused-cli --version
```

For automated or non-interactive installs, set `ASSUME_YES=1` to skip the confirmation prompt.

## Sign in

```bash
fused-cli login
```

This opens your Engine's sign-in page and saves a subject-scoped credential after you approve it. The credential never passes through the browser and is never printed.

```bash
fused-cli whoami
```

<Note>
  On a headless machine, `fused-cli login --no-browser` prints the URL instead of trying to open one.
</Note>

## Choose your service's authentication

For a supported OAuth integration, [use a Managed service](/workspace/use-managed-service) to connect users without registering your own provider app. Alternatively, [store your own credentials](/bucket/store-credentials). Managed auth is an explicit app configuration choice; init does not automatically choose it when local credentials are missing. Use `--no-apply` while preparing the managed reference, then plan and apply the completed config.

## Create an App

```bash
fused-cli init support-app --service linear
```

Without a method flag, `fused-cli init` creates one App with SDK, MCP, and REST delivery. It searches your workspace and then the Registry, pins a concrete service version, and asks which operations the App should expose. **All operations** is highlighted by default. Open **Choose operations…** to search by operation ID, method, path, summary, or tag. You do not need to know operation IDs before you start.

If activation is needed, the CLI shows one combined confirmation. It writes separate workspace and App receipts. Missing provider credentials do not block creation: in a terminal the CLI offers to store them securely and retry planning once, while skipping that optional step still publishes the App.

When the command succeeds, Fused applies one immutable App version, downloads its typed SDK package, and reports its hosted MCP URLs. REST execution uses that same version ID and token. Init writes one `kind: sdk` config with nested `mcp` delivery, plus a workspace config if service activation was needed.

If no suitable Registry service exists, [import the API yourself](/workspace/bring-your-own-api) from a spec, a GraphQL endpoint, or the provider's documentation.

<Warning>
  The first successful initialization prints the App execution token **once**. Capture it now — a repeat apply will not show it again.
</Warning>

<Note>
  Automating this? Run `fused-cli init support-app --service linear --select-all linear --no-input`. No method flag is needed for the combined App. Missing credentials are reported as readiness metadata without blocking publication. You may pre-provision them with `secret set --no-input --value-stdin`, or let the first affected call return the exact safe setup command. Use an explicit `--operation` when the App needs a narrower surface. For structured plan and apply output, use the [advanced controlled workflow](/advanced/control-the-workflow).
</Note>

## Call it

The SDK, MCP server, and REST endpoint use the same selected operations and execution token.

| Way | Reach for it when | What it needs |
|---|---|---|
| `fused-cli sdk invoke` | Checking the path works, or trying an operation by hand | The CLI and the token |
| The typed package | Your application calls this for real | The downloaded package and the Engine's **gRPC** address |
| `POST /v1/apps/{id}/executions` | You are not in TypeScript or Python, or you would rather not ship a package | The Engine's **HTTP** address and the version ID from apply |
| Hosted MCP | An agent discovers and executes selected operations | The stable MCP URL from apply or the App details page |

<CodeGroup>

```bash CLI
export FUSED_SDK_TOKEN='...'

fused-cli sdk invoke support-app@1.0.0 issueUpdate \
  --params '{"id":"ISS-42","state":"done"}'
```

```typescript Typed package
import { FusedSDK } from 'support-app';

const sdk = new FusedSDK({
  grpcUrl: process.env.FUSED_ENGINE_GRPC_URL,
  token: process.env.FUSED_SDK_TOKEN!,
});

const result = await sdk.Linear.issueUpdate({ id: 'ISS-42', state: 'done' });
if (result.ok) console.log(result.data);
```

```bash REST
curl -X POST "$FUSED_ENGINE_URL/v1/apps/$VERSION_ID/executions" \
  -H "Authorization: Bearer $FUSED_SDK_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"operation":"issueUpdate","input":{"id":"ISS-42","state":"done"}}'
```

</CodeGroup>

A call returns `{ ok, status, data, error }` rather than the payload itself, and services sit on the client in PascalCase with operations following the provider's own grouping — so `issueUpdate` may be `sdk.Linear.issues.update`. [Using it in your app](/app/use-in-your-app) covers the whole shape; your package's generated `README.md` lists the exact paths for the operations *you* selected.

Whichever one you used, the receipt is the same:

```bash
fused-cli sdk activity support-app@1.0.0
```

It shows what ran, how long the provider took, and what came back.
