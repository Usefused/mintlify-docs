Before you start generating SDKs and MCP servers, it helps to understand the model Fused uses to represent integrations. Fused separates concerns cleanly: a **service** captures everything Fused knows about an API, and **artefacts** are the typed, versioned outputs your teams consume. Everything flows from a single service definition, so there's one place to update when an upstream API changes, and every artefact inherits that update automatically. The sections below walk through each building block in the order you'll encounter them.

## Artefacts at a glance

Every service can produce any combination of these three artefact types:

## Services

A **service** is Fused's representation of an external API. When you ingest an API definition — an OpenAPI spec, a GraphQL schema, a Postman Collection, a documentation URL, or a plain-English description — Fused parses it into a versioned service that captures:

- **Endpoints** — every operation the API exposes, with parameter shapes and response types.
- **Authentication** — the auth schemes the API supports (API key, OAuth 2.0, Bearer token, etc.) and how to wire them up.
- **Webhook events** — any events the API can push to your application.
- **Operational settings** — base URLs, rate-limit hints, pagination patterns, and retry behaviour.

Services are the single source of truth. Every artefact Fused generates — SDKs, MCP servers, webhook receivers — is derived from the same service definition. Update the service (manually or via drift detection), and all downstream artefacts can be regenerated from that updated definition.

<Note>
  Fused maintains a registry of pre-ingested services for popular APIs (Jira, GitHub, Slack, Stripe, and many more). You can use these directly without supplying your own spec.
</Note>

## Artefacts

An **artefact** is any output Fused generates from a service. The three artefact types are:

- **Typed SDK** — a TypeScript or Python package with fully typed methods for each scoped endpoint.
- **MCP Server** — a Model Context Protocol server exposing `search_docs` and `execute_tool` capabilities, deployable to Fused-Run (TypeScript) or self-hosted (TypeScript or Python).
- **Webhook Receiver** — a managed outbound WebSocket connection that streams typed events from an API to your application.

One service can produce multiple artefacts simultaneously. If your platform team ingests the Stripe service, they can publish a typed SDK for the billing team, an MCP server for your AI copilot, and a webhook receiver for your event pipeline — all from the same service definition, all staying in sync when Stripe's API changes.

## SDK Scoping

Not every team needs every endpoint in a service. **SDK scoping** lets you select exactly the subset of operations your SDK will expose. You do this interactively in the **Cart UI** (available in the browser after running `fused-cli create`) or by passing `-y` to skip the UI and accept all resolved endpoints automatically.

Scoping has two practical benefits:

1. **Smaller surface area** — your generated package only includes the types and methods your team actually calls, reducing bundle size and cognitive overhead.
2. **Enforced intent** — a scoped SDK makes it impossible to accidentally call an endpoint your team shouldn't be using, which is especially valuable in regulated environments.

<Tip>
  You can always widen a scope later by regenerating the SDK with additional endpoints selected. Existing call sites won't break — the new methods simply become available alongside the ones already in use.
</Tip>

## Business Capability SDKs

A **business capability SDK** bundles multiple services into a single typed package organised around a business domain rather than an individual API. Instead of your onboarding workflow importing separate Jira, GitHub, and Slack clients, it imports one `onboarding-sdk` that exposes `sdk.jira`, `sdk.github`, and `sdk.slack` under a unified initialisation interface.

Business capability SDKs are created by passing a natural-language description to `fused-cli create`. Fused resolves the required services from its registry, scopes each one to the relevant endpoints, and publishes the bundle as a single versioned npm package.

The `FusedSDK` constructor accepts a credential object with one key per bundled service:

```typescript
import { FusedSDK as OnboardingSDK } from "@acme/onboarding-sdk";

const sdk = new OnboardingSDK({
  jira:   { token: "jira_..." },
  github: { token: "ghp_..." },
  slack:  { token: "xoxb_..." }
});
```

Each service authenticates independently, and the generated SDK carries no vendor runtime dependency — the code your team installs is fully owned by you.

## MCP Tools

Every MCP server Fused generates exposes exactly two tools to the consuming AI agent or LLM:

- **`search_docs`** — performs semantic search over the SDK's documentation and endpoint descriptions. The agent calls this to discover what operations are available and understand their parameters before attempting to use them.
- **`execute_tool`** — accepts a TypeScript code snippet and runs it against the SDK in a secure, sandboxed environment. The agent writes code; Fused executes it safely and returns the result.

This two-tool design means AI agents never make raw HTTP calls to third-party APIs. All execution is mediated through the typed SDK, which enforces parameter validation and authentication, and through the sandbox, which applies rate limiting and audit logging.

<Warning>
  `execute_tool` runs code in an isolated sandbox with no access to your application's runtime, filesystem, or secrets beyond the credentials you explicitly provision for the MCP server. Never pass secrets inside the code snippet itself.
</Warning>

### MCP hosting options

TypeScript MCP servers can be deployed directly to **Fused-Run** (Fused's managed cloud) by passing `--deploy` to `fused-cli create` or `fused-cli update`. The CLI outputs a stable HTTPS endpoint your AI clients connect to immediately.

Python MCP servers **must be self-hosted** — pass `--language python` without `--deploy` to download the source, then run it in your own infrastructure.

## Webhook Receivers

**Webhook receivers** solve the public-ingress problem. Most webhook providers require your server to expose a public HTTPS endpoint. In development, staging, or private-network environments, that's often impractical.

Fused provisions an **outbound WebSocket connection** from its infrastructure to your application. Your app connects outbound to Fused's WebSocket endpoint, and Fused forwards incoming webhook events over that connection as fully typed messages.

Register a receiver and attach typed event handlers using the `fusedWebhooks` helper exported from your generated package:

```typescript
import {
  FusedSDK as OnboardingSDK,
  fusedWebhooks,
  JiraWebhook,
  GithubWebhook
} from "@acme/onboarding-sdk";

const sdk = new OnboardingSDK({
  github: { token: "ghp_..." },
  slack:  { token: "xoxb_..." }
});

const receiver = fusedWebhooks.registerReceiver("onboarding", "fused_api_key");

// Fires when a Jira issue is created
receiver.on(JiraWebhook.ISSUE_CREATED, async (event) => {
  const { issue } = event.body;
  if (issue.fields.project.key !== "ONBOARD") return;

  await sdk.github.repos.addCollaborator({
    owner: "acme-corp",
    repo: "platform",
    username: issue.fields.assignee.accountId,
    permission: "push"
  });
});

// Fires when GitHub confirms member access
receiver.on(GithubWebhook.MEMBER_ADDED, async (event) => {
  const { member, repository } = event.body;
  await sdk.slack.chat.postMessage({
    channel: "#engineering",
    text: `👋 ${member.login} now has access to ${repository.name}. Welcome!`
  });
});
```

`fusedWebhooks.registerReceiver(name, apiKey)` establishes the outbound WebSocket connection. `receiver.on(EventEnum, handler)` registers a typed handler for a specific event. You get:

- **No public ingress** — your server never needs to be reachable from the internet.
- **Typed payloads** — event schemas are derived from the service definition, so every message is typed and validated before it reaches your handler.
- **Managed retries** — Fused buffers and retries delivery if your connection drops.

## Drift Detection

APIs change. Providers add fields, deprecate parameters, rename operations, and update authentication flows. **Drift detection** is Fused's mechanism for keeping your service definitions — and therefore all their artefacts — current.

Fused monitors upstream API definitions on a scheduled basis. When it detects that a service definition no longer matches the live API spec, it:

1. Flags the service as **drifted** in your dashboard.
2. Shows a diff of what changed.
3. Lets you review and accept the updated definition before regenerating artefacts.

<Info>
  Drift detection is non-destructive. Fused never automatically regenerates artefacts when drift is detected — you always review the diff and confirm before anything changes in your downstream packages.
</Info>

## Fused-Run

**Fused-Run** is Fused's managed cloud hosting environment for TypeScript MCP servers. When you generate a TypeScript MCP server artefact and pass `--deploy`, Fused-Run handles:

- **Deployment** — your MCP server is hosted at a stable HTTPS endpoint with no infrastructure setup required.
- **Sandboxing** — `execute_tool` calls run in isolated containers with enforced timeouts, memory limits, and network egress policies.
- **Scaling** — Fused-Run scales execution capacity automatically based on request volume.
- **Audit logging** — every `execute_tool` invocation is logged with the code that was run and the result returned.

You can point any MCP-compatible AI client — including Claude, Cursor, and compatible LLM frameworks — directly at your Fused-Run server URL.

<Note>
  Python MCP servers cannot be deployed to Fused-Run and must be self-hosted. See the [MCP self-hosting guide](/guides/mcp-self-host) for setup instructions.
</Note>
