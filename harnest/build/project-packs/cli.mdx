Build your [pack folder](/harnest/build/project-packs/create) into a wheel with `harnest pack build`. The generated executable forwards commands to Harnest and attaches your pack to initialization, upgrades, and Studio.

## Use a pack directly

```bash
harnest init support-bot --pack ./acme-pack --option team=customer-success --dry-run --json
harnest init support-bot --pack ./acme-pack --option team=customer-success
harnest upgrade support-bot --pack ./acme-pack
harnest upgrade support-bot --pack ./acme-pack --apply
harnest studio --pack ./acme-pack --option team=customer-success
```

Repeat `--pack` to select several packs in execution order. Without `--pack`, `harnest upgrade` runs core migrations only; it does not execute pack hooks. Studio forwards `--option` values to project initialization.

## Declare the command

Pack identity and the executable name belong in `pack.yaml`:

```yaml pack.yaml
apiVersion: harnest.dev/pack/v1
name: acme
version: 1.0.0
title: Acme agents
command: acme-agent
```

If `command` is omitted, the executable uses the pack name. Keep project hooks in `pack.py`, exporting `pack = ProjectPack(schema_version=1, ...)`. The manifest supplies its name when Harnest loads the folder.

## Build the branded command

```bash
harnest pack validate ./acme-pack
harnest pack build ./acme-pack --output ./dist
python -m pip install ./dist/harnest_pack_acme-1.0.0-py3-none-any.whl
acme-agent --help
```

The wheel contains the pack and a launcher with no Python package dependencies. Install Harnest separately; set `HARNEST_CLI` to an executable path if it is not on `PATH`. The Harnest CLI prepares its bundled Studio runtime on first launch; standalone Python integrations need Studio installed in their environment. Pack `requires` ranges validate compatibility; they do not install dependencies.

Building validates the Studio sub-pack when Studio is installed. The wheel contains the pack folder except caches, build output, virtual environments, `node_modules/`, and `.env` files. Symlinks are rejected, and unchanged pack inputs produce a byte-identical wheel.

## Commands and flags

| Command | Behavior |
|---|---|
| `acme-agent init DIRECTORY` | Run Harnest initialization with the installed pack; `--dry-run` previews the combined plan. |
| `acme-agent upgrade DIRECTORY` | Preview Harnest and pack migrations; `--apply` applies the combined plan. |
| `acme-agent studio` | Open Studio with the pack's `studio:` resources, defaults, and UI. |
| A registered company command | Run the pack handler with the remaining arguments. |
| Any other command | Forward arguments to Harnest and preserve its exit code. |

```bash
acme-agent init support-bot --option team=customer-success --dry-run --json
acme-agent init support-bot --option team=customer-success
acme-agent upgrade support-bot
acme-agent upgrade support-bot --apply
acme-agent test support-bot
```

A later apply builds a fresh plan. `--json` prints a plan without file contents or option values; it does not make an applying command read-only. Pack planning returns `2` for blockers, `1` for operational errors, and `0` for success. Other commands retain their own exit codes.

## Initialize from a template

```bash
acme-agent init ./sales --template acme-sales --option team=sales
```

`--template` accepts a template project name, short slug, or HTTPS wheel URL. Use `--template-sha256` to pin a wheel:

```bash
acme-agent init ./sales \
  --template https://packages.example.com/acme_sales.whl \
  --template-sha256 "$TEMPLATE_SHA256" \
  --option team=sales
```

Harnest renders the template in staging before running pack initializers. Its framework and mode determine the target; do not combine `--template` with `--framework`, `--mode`, `--minimal`, or `--example`. `--template-sha256` requires `--template`. For the built-in scaffold, the default framework is ADK and the default mode is managed.

Use `--dry-run` to review changes without creating the destination. Planning may download the template; download or validation failures stop before pack hooks run.

## Typed pack options

Declare a Pydantic options model in `pack.py` and pass values with repeated `--option key=value` flags:

| Model input | CLI example |
|---|---|
| String | `--option team=customer-success` |
| Integer | `--option replicas=2` |
| Enum | `--option environment=production` |
| Boolean | `--option enabled=true` |
| List or object | `--option 'regions=["eu-west", "us-east"]'` |

With multiple packs, prefix each field with its pack name, such as `--option acme.team=support`. Lists and objects are decoded as JSON; the options model validates and coerces the resulting values. Hyphens in option keys become underscores. Defaults belong in that model.

Options are not stored in `harnest-packs.lock`. During upgrades, `context.options` is `None` unless the caller supplied options for that pack. Read persisted choices from company configuration when no new inputs were supplied.

## Add a company command

Add a handler to the same `pack.py` that defines your pack. It receives a list of argument strings and returns an exit code or `None` for success:

```python pack.py
import argparse
from pathlib import Path

@pack.command("inspect-company", help="Locate the company's agent configuration")
def inspect_company(arguments: list[str]) -> int:
    parser = argparse.ArgumentParser(prog="acme-agent inspect-company")
    parser.add_argument("directory", type=Path)
    options = parser.parse_args(arguments)
    path = options.directory / "acme-agent.yaml"
    print(f"Company configuration: {path}")
    return 0 if path.is_file() else 1
```

Try the handler before building a wheel:

```bash
harnest pack run ./acme-pack inspect-company ./support-bot
```

After installing the wheel, use `acme-agent inspect-company ./support-bot`. Harnest command names are reserved. Custom handlers own their work and error handling; they do not automatically participate in a project transaction.

## Include your company's Studio

Add a [`studio:` section](/harnest/studio/packs) to the same `pack.yaml`, then rebuild and install the wheel:

```bash
acme-agent studio --workspace ./agents
```

The launcher attaches the installed pack automatically. Studio reads its manifest, resources, builder defaults, and UI without importing `pack.py`. JavaScript module contributions still require explicit trust, for example `--trust-ui-pack acme`.

Studio's **Create agent** action uses Harnest initialization with the loaded project packs. Supply required initialization values with `--option team=support` when launching Studio, or define defaults in the pack's options model. Resource-template installation remains a separate reviewed source-installation flow.

Use **Restore default UI** (`?safe-ui=1`) to recover the bundled interface. To exclude a broken pack entirely, launch `harnest studio --workspace ./agents` without `--pack` instead of using the branded executable.

For Python integrations, use [`load_pack` and `ProjectPlanner`](/harnest/build/project-packs/plans-and-recovery). `load_pack(path, import_project=False)` reads manifest metadata without importing project hooks; its `project` is `None`. Use the default loading mode before passing project hooks to the planner. For browser pack code, use the [Studio TypeScript contract](/harnest/studio/mods#typescript-and-ide-support).
