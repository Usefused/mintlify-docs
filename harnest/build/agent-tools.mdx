Agent Tools let a model act through typed, testable capabilities. Choose where each capability should run.

| Tool type | Runs in | Best for |
|---|---|---|
| `@tool` | Agent server | Business logic and provider calls |
| `@client_tool` | Browser, desktop, or mobile host | UI and device capabilities |
| MCP tool | Remote MCP server | External capability servers |

## Discovery properties

| Property | Rule |
|---|---|
| Location | `tools/<name>.py` |
| Export | One callable matching the filename |
| Description | Docstring or decorator description |
| Arguments | Structured values |
| Results | Structured values, optionally validated by Pydantic |
| Credentials | Resolve through `context.credentials`, never tool arguments |
| Runtime permission | Optional stable identifier declared with `permission=` |

## Choose an approval boundary

| Need | Use |
|---|---|
| Every call requires permission | `@require_human_approval` |
| Evaluation finds one risky operation | `request_human_approval(...)` |
| Remote operation requires permission | Approval policy on the MCP client |

Approval resumes the exact suspended task without replaying earlier work.

## Project tools for one invocation

Declare a stable permission on a server or client-hosted tool when different
authenticated callers should receive different model capabilities:

```python tools/create_invoice.py
from harnest.tool import tool


@tool(permission="billing.invoice.create")
async def create_invoice(customer_id: str):
    """Create an invoice for a customer."""

    return {"customerId": customer_id, "status": "created"}
```

`@client_tool(permission="device.location.read")` uses the same contract. An
application can create an `AgentRuntimePrincipal` after it authenticates and
authorizes a request, then pass it as `agent_principal=` when invoking the
managed agent. Harnest omits permissioned tools whose identifiers are not
granted and rechecks the permission before execution. Advanced native apps are
rejected when an Agent Runtime Principal is supplied because Harnest cannot
guarantee projection inside an arbitrary framework-owned graph. For the same
reason, a managed LangGraph `Graph` containing `Agent.advanced(...)` or a raw
native `Pregel` node rejects restricted invocations; use managed `Agent` nodes
throughout a permission-projected graph.

Unpermissioned tools remain available. Omitting `agent_principal` preserves the
existing unrestricted behavior; passing a principal with no grants hides every
permissioned capability. Harnest gives each principal an opaque generated ID,
owns its invocation binding, and does not publish it through `context`.

Local nested agent calls inherit the active principal when
`agent_principal` is omitted. They may pass a principal with fewer grants, but
cannot add permissions to the active invocation.

<Warning>
  Runtime projection is a convenience and defense-in-depth boundary, not a
  replacement for authentication or authorization at your application gateway.
</Warning>

See [Custom HTTP endpoints](/harnest/runtime/custom-http-endpoints) for the
gateway-to-agent handoff and [MCP client](/harnest/build/mcp-client) for remote
capability permissions.
