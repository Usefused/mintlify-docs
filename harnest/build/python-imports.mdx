Import each capability from its public domain module. The examples in this documentation use these paths so you can find related types and operations in one place:

```python
from harnest.agent import Agent, AgentRuntimePrincipal, client_tool, tool
from harnest.auth import AuthPrincipal, AuthenticationError
from harnest import context, cron, lifecycle
from harnest.sandbox import Sandbox, control
```

The package root exposes feature namespaces only. Classes, decorators, functions, errors, and types stay in the feature module that owns them.

Find signatures, fields, and methods in the [Python API reference](/harnest/reference/api/overview). Each public module has its own page, including [Tasks](/harnest/reference/api/task) and [Cron](/harnest/reference/api/cron).

The implementation path `harnest.context_agent` has been removed. Use `from harnest import context` for `context.agent` operations and `from harnest.context import AgentSession, AgentResponse` for their contracts. Modules prefixed with `_` are private implementation details.

The `harnest.task_storage` implementation path has also been removed. Import `TaskRecord`, `TaskStore`, and `TaskStoreConflictError` from `harnest.task`. Run `harnest upgrade AGENT_DIR --apply` to rewrite supported imports in an existing project. Imports or uses of private storage helpers require manual review.

## IDE autocomplete and hover help

Synchronize the managed environment to enable typed completion and hover documentation:

```bash
harnest env sync .
```

Sync creates `.venv` and configures the default interpreter in `.vscode/settings.json` for compatible editors. If your editor already selected another interpreter, select `.venv/bin/python` manually (`.venv/Scripts/python.exe` on Windows). Other IDEs can use the same environment.

Codex desktop, Codex CLI, and Antigravity 2.0 are separate agent applications.
For Python commands in these agents, use `.venv/bin/python` directly; their
terminal commands do not inherit the VS Code Python interpreter setting.

Harnest preserves any `.venv` it does not own and prints the managed interpreter for manual selection. Keep `.venv` out of version control.

Harnest includes static declarations for its lazy domain namespaces and invocation context. Editors can discover methods and signatures on `harnest.context`, `context.agent`, `context.session`, `context.mcp`, `context.skills`, and the other context capabilities without running an agent. Context values still resolve for each active invocation; do not access them at module import time.

Core functions and methods carry parameter and return annotations. Static consumer checks cover public classes, inherited methods, properties, and protocol methods across Harnest's domains. Task, context-provider, and lifecycle decorators preserve the authored callable's parameters and result type, so an editor can flag invalid direct calls:

```python
from harnest.task import task


@task
async def customer_label(customer_id: str) -> str:
    return customer_id


async def example() -> str:
    return await customer_label("customer-123")
```

The direct call above retains its `str` argument and result types. Deferred task arguments are validated at runtime; `.defer()` accepts scheduling options and returns a `TaskHandle`. Dynamic payloads and resource lookups without an expected class may still use `Any`.

For application-defined resources, pass the expected class to preserve its completion and return type:

```python
from harnest import context
from my_company.customers import CustomerDirectory


def customer_label(customer_id: str) -> str:
    directory = context.resource("customers", CustomerDirectory)
    return directory.label(customer_id)
```

Here, your application supplies and registers `CustomerDirectory`. `context.storage("name", ExpectedType)` and `context.extensions("name", ExpectedContext)` also preserve the supplied type. Lookups without an expected type return `Any`; Harnest cannot infer a company's resource type from a runtime string. Runtime type validation remains in place.

The managed wheel also includes editor-only definitions for
`harnest.extensions.docker` and `harnest.extensions.hatchet`. Those imports get
completion and hover help while the actual modules remain available at runtime
only when their corresponding official extension is installed in the project.

Run `env sync` after dependency changes. Harnest retargets its `.venv` link when
the content-addressed runtime changes, so an automatically detected interpreter
continues to resolve the current environment.

## Scoped operations

Sandbox execution and cleanup share a namespace:

```python
from harnest.sandbox import control

with control.execute(timeout_seconds=30) as execution:
    execution.check()
    # Perform provider work with execution.remaining() as the I/O budget.

with control.cleanup(timeout_seconds=5) as cleanup:
    cleanup.check()
    # Release owned resources using cleanup.remaining() as the I/O budget.
```

[`control.current()`](/harnest/reference/api/sandbox#control-current) returns the active scope. See [sandbox failure recovery and cleanup](/harnest/build/sandboxing#failure-recovery-and-cleanup) for cancellation and deadline guarantees.

Query lifecycle coverage with the same domain pattern:

```python
from harnest import lifecycle

coverage = lifecycle.coverage("langgraph", "managed")
```

## Public API stability

Public module exports, annotations, and docstrings are checked by the release gate. Re-exports preserve object identity, including exception classes.

During `0.x`, Harnest may make a breaking public Python API change only in a
minor release. Public names and signatures are otherwise backward compatible;
deprecated APIs remain available for at least one minor release before removal,
except when retaining them would preserve a security defect. Patch releases do
not intentionally break these contracts.

Serialized plans, locks, manifests, and HTTP documents have independent format versions.
