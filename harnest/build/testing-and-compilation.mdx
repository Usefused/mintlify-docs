Harnest owns the environment and compiled application used by every test lane. Authored tests exercise the selected ADK or LangGraph target without importing Harnest or manually loading build artifacts.

| Lane | Command | Network | Best for |
|---|---|---:|---|
| Unit | `harnest test AGENT_DIR` | No | Agent logic and local tools |
| Smoke | `harnest test AGENT_DIR --smoke` | Allowed | Live models, MCP, and API journeys |
| Evals | `harnest test AGENT_DIR --evals` | Depends on eval | Quality and tool trajectories |
| Compile | `harnest compile AGENT_DIR` | No | Reproducible standalone artifact |

## Review changes in Agent Builder

Playground provides conversation testing, traces, and evaluation suites. Agent authoring, visual editing, and MCP setup live in the standalone Harnest Studio; Playground no longer includes an embedded Studio tab.

Harnest Studio is bundled with the release CLI, including its web server, browser assets, and compiled AI authoring assistant. Start it from the folder you want to use as your workspace:

```bash
harnest studio
```

If `--workspace` is omitted, Studio uses your current working directory. Select a different existing folder or port explicitly:

```bash
harnest studio --workspace /path/to/agents --port 1940
```

Studio finds agent folders recursively under the workspace and displays relative paths. **Refresh** finds new agents; **Open folder** adds one elsewhere. Discovery skips generated, hidden, dependency, and symlinked directories. Choose a narrower workspace if it exceeds 10,000 scanned folders.

Open the private launch URL printed in the terminal. Studio defaults to `127.0.0.1:1940`. First launch may download runtime dependencies; later launches reuse them. Configure model credentials for **Build agent**.

Keep the command running while using Studio. Ctrl+C stops its local server and supervised processes. An explicit `--python` or `HARNEST_PYTHON` uses that interpreter instead, which must already contain Studio and its matching dependencies.

### Describe and build your agent

Enter what your agent should do and choose **Build my agent**. In the creation dialog, choose a **Builder model** and **Agent name**. Expand **Project settings** to change the save folder, framework, authoring mode, or starting point. Studio defaults to a minimal project. Leave the description blank to create source without asking the model for changes.

After creating a project from a description, Studio sends that description and the initial source to your configured builder model. For existing projects, use **Build agent** to request changes or ask questions. The assistant can ask for clarification before proposing files; reply in the same conversation.

Open **Context & permissions** to choose the initial files shared with your model provider. **Allow AI to read related project source** is enabled by default; turn it off to share only selected files. Related-source access lets the assistant read up to 24 files and 160 KiB across two additional rounds. Proposals list files read; hidden files, secrets files, generated content, and symlinks are excluded.

Studio shows live builder activity and elapsed time. Choose **Stop** to cancel the current request. A cancelled or incomplete response does not apply source changes. If a proposal fails path, revision, or source-syntax checks, Studio attempts one repair against the same authorized source snapshot before offering it for review. These checks do not replace compilation or tests.

Choose **Review changes**, inspect the diff, then choose **Apply to project**. Save editor changes first; revision checks protect concurrent edits. Applied proposals leave a confirmation and file list in the conversation. Recent conversation context helps with follow-up requests, while the current source remains authoritative. Use **Compile** and **Commands** to validate the result.

### Run, try, and refine

Follow **Build agent → Connect tools → Try agent** to test the agent you authored:

1. Save source changes, then choose **Run agent**. Studio prepares the environment and starts a supervised local development server. Wait for the ready status; open **Server output** if startup fails.
2. In **Try agent**, enter a message and choose **Send message**. These messages go to your running agent and can invoke its connected tools. Studio does not automatically retry failed messages, because a tool action may already have completed.
3. Expand **Run details** to inspect the response, tool evidence, and duration. Choose **Refine this response** or **Create a test** to prepare a request in **Build agent**. Review and send that request, then review any proposed source changes before applying them. When creating a test, specify the expected behavior if the observed response was wrong.

Builder conversations and test conversations remain separate. Studio retains each project's conversations and drafts while you switch projects in the same browser session. **New conversation** starts a fresh agent session. A server restart also starts a fresh session for the next message.

Use **Continue in Playground** for an interaction that needs approval or private client input, or **Open Playground** for the full runtime interface. Agents that require sign-in must be tested in Playground. To test streaming AG-UI behavior, select **AG-UI** there; Studio's **Try agent** uses the native response API.

Studio supervises one preview server at a time. Choose **Stop server** before starting another project's agent. Closing Studio with Ctrl+C stops its supervised server.

### Add runtime and evaluation capabilities

Use the component palette to create current Harnest authoring contracts:

| Component | Choices and next step |
| --- | --- |
| **Cron schedule** | Create a fixed UTC `@cron` function, a dynamic target, or a schedule for an existing task. Set arguments, queue, and retry policy; existing tasks retain their own policy. |
| **Task and cron storage** | Choose memory for local development, Postgres, or Redis. The generated factory shares one provider across both roles. Replace existing providers for those roles before compiling. |
| **Private client input** | Create a typed private schema and handler. Implement the consuming operation before serving; only the fixed authored response reaches the model. |
| **Evaluation** | Choose a preset from the installed CLI, including custom metrics. ADK and LangGraph share the evaluation lane. Existing criteria are preserved; judge, simulator, and Vertex presets need their scoring backend configured. |
| **AG-UI transport** | Review an explicit `server.agui` setting, apply it, then rebuild and restart. It defaults to enabled; environment references remain unchanged until you apply a choice. |
| **Custom UI event** | Scaffold an async tool using `await ui.emit("app.event", payload)`. Your frontend owns the widget; Playground shows the event as inert JSON. |
| **AG-UI smoke test** | Add a test of the `/agui` SSE initialization handshake. The empty run creates a thread without invoking a model. Run it with **Commands → Run smoke tests** against a running agent. |

Dynamic cron targets have no schedule until runtime code calls `harnest.cron.create` or you create one in the serving agent's **Work** view. Choose **Commands → Start development server**, then use **Tasks & schedules** beside the command output to open that view. Learn more about [scheduled tasks](/harnest/build/scheduled-tasks) and [task storage](/harnest/runtime/task-storage).

Managed environments include Postgres and Redis drivers. Use **Commands → Sync dependency environment**, then supply the selected provider's `DATABASE_URL` or `REDIS_URL` at runtime. Memory task storage loses jobs and schedules when the process exits. Configure Redis persistence for durable use.

Evaluation creation runs `harnest add eval` and shares its current presets. `custom` creates a scorer stub to implement and register in `evals/test_config.json`. Criteria apply across the project's evaluation sets. Run **Compile** after adding components, then use **Commands** for the appropriate checks. Live evaluations invoke the agent's configured models and tools.

**Commands → Run evaluations** lets you choose **Business** matching (required tool calls in order, with extra calls allowed) or **Strict** matching (the exact authored call sequence). **Sync dependency environment** lets you select the runtime, compile, development, or evaluation profile; Studio forwards that choice to `harnest env sync --profile`. Keep the resulting lock files with your project.

Playground labels private input separately, displays the input schema, and clears submitted values from its form on both success and failure. Pending private input requires the same serving process. Select **AG-UI** in Playground for streaming conversation testing. Its continuation form submits every pending approval or client input together; private values are excluded from messages and state.

### Manage running work

The serving agent's **Work** view lists task metadata and dynamic schedules for the authenticated owner. Look up a task by ID, inspect its status, and cancel pending or running work. Create schedules against deployed cron functions, edit their UTC expression and arguments, pause or resume them, cancel them permanently, or delete their definition. Edits reject stale revisions. Cancelling or deleting a schedule does not cancel task occurrences already enqueued; cancel those tasks separately.

Fixed schedules remain source-controlled: edit `cron/`, rebuild, and restart. Application automation is a separate owner. A trusted authenticator must issue the claim `harnest:work:automation` with boolean value `True` to enable that scope; browser headers or an ordinary user identity do not grant it. Work routes exist only with the development Playground enabled.

Memory, PostgreSQL, and Redis support bounded listings without task payloads. Redis upgrades its existing task index incrementally; **Continue indexing existing tasks** completes the scan before listing. Existing custom providers keep lookup and cancellation support; add the optional metadata queries described in [task storage](/harnest/runtime/task-storage) to enable browsing.

### Set Studio AI budgets

Click **Configure** in **Build agent** to choose a model timeout of 1–1800 seconds and a maximum output budget of 1–131072 tokens. Defaults are 120 seconds and 12000 tokens. These settings apply to subsequent requests; your provider can impose a lower output limit. The timeout applies to each provider call, and a proposal may involve multiple calls or source-reading rounds.

Set host defaults before starting Studio:

```bash
export HARNEST_BUILDER_TIMEOUT_SECONDS=240
export HARNEST_BUILDER_MAX_TOKENS=16000
harnest studio
```

Saved browser choices override these defaults. Studio restarts its private assistant when the model or budgets change and derives longer runtime and HTTP deadlines from the selected timeout. Provider credentials remain server-side.

### Connect and create MCP servers

Choose **Connect tools** or open **MCP connections** in the workspace sidebar. Choose **Add HTTP MCP endpoint** to connect an existing Streamable HTTP server, or enter your Fused Engine URL and choose **Connect Fused**. Complete sign-in in the same browser, then reopen the dialog. Management credentials remain in Studio's server memory; restarting Studio requires reconnecting.

After connecting, choose **Add existing Fused MCP** to select an active server version, or **Create MCP with Fused** to select workspace services and their operations. Choose the owning agent, the Fused bucket, and an optional owner team. An empty operation selection is rejected; **All operations** must be selected explicitly. Provider connections and bucket permissions must already be configured in Fused.

**Review connection** shows the exact provisioning configuration and source diffs. **Apply connection** can create a server, issue a seven-day execution token, and write the owning agent's MCP Client. It also adds runtime environment references to an existing `harnest-deployment.yaml`; select a deployment agent name if that manifest contains multiple agents. Studio checks source revisions before provisioning. If the remote result is uncertain, check Fused's server list before preparing another review; Studio does not replay that mutation automatically.

Runtime credentials are stored outside project source in owner-only files under `~/.harnest/studio-credentials`. Set `HARNEST_BUILDER_CREDENTIALS_DIR` before starting Studio to choose another private directory. Studio supplies these bindings only to commands for that project and redacts execution tokens from command output. Restart an already-running agent after applying a connection. For commands launched outside Studio or deployments managed elsewhere, provide the variables shown in the review through your own secret manager. Disconnecting Fused clears management access and pending reviews; it does not revoke existing MCP execution tokens.

To let **Build agent** discover Fused operations, enable **Allow Fused service and operation metadata to be shared with the model**. This separate permission is off by default. The model can propose a plan but cannot access credentials or apply it.

### Delete and restore capabilities

Select a capability and choose **Delete capability…**. Review affected files and references first. Deleting a package entrypoint removes the whole package from discovery; root files and category folders are protected.

Deleted files remain recoverable under `.harnest/builder-deleted/`. Use **Deleted capabilities → Restore**; restoration refuses to overwrite existing paths. Stop builds and previews first.

Explicit imports, graph node references, schedules, and other authored wiring are not rewritten. Review the possible references and build the agent after updating them. Deleting source does not remove a deployed container, an external service, or its database data.

## Unit tests

Run the default offline lane:

```bash
harnest test AGENT_DIR
```

Harnest compiles the project, then collects `tests/unit/test_*.py`.

| Fixture | Value |
|---|---|
| `agent` | Selected framework target |
| `tools` | Read-only map of local tools |

Unit tests should not call models, MCP servers, or other networks. This is a convention, not an OS sandbox.

## Smoke tests

Live runtime checks belong in `tests/smoke/test_*.py` and run only when selected:

```bash
harnest test AGENT_DIR --smoke
```

The unit lane runs first. Smoke tests add a FastAPI `client` and a `smoke` fixture.

Use [SmokeClient.respond](/harnest/reference/api/testing#smokeclient-respond) for one JSON response or [SmokeClient.stream](/harnest/reference/api/testing#smokeclient-stream) to collect ordered SSE events.

Smoke tests may spend time or money and use real credentials. Run them deliberately.

## Evaluations

Run eval assets after the Python tests:

```bash
harnest test AGENT_DIR --evals
harnest test AGENT_DIR --smoke --evals
```

Both frameworks use ADK evaluation assets. Save the complete `EvalRunResult` with `--eval-output FILE`, including when using `--no-output`.

## Compile an artifact

Compile validated source into a standalone runtime directory:

```bash
harnest compile AGENT_DIR --output .harnest/my-agent
```

| Artifact file | Purpose |
|---|---|
| Preserved source | Your agent code |
| Generated adapters | Selected framework integration |
| `harnest-manifest.json` | Versions, mode, and source identity |
| `harnest-build-report.json` | Included files, reasons, and byte sizes |
| `server.yaml` | Mutable runtime settings |
| `harnest-agent` | Launcher |

Compiled directories are reproducible output. Do not edit or commit them.

### Conditional dependencies

| Source | Compile behavior |
|---|---|
| Root `pyproject.toml` | Resolves application dependencies |
| Harnest Extension `pyproject.toml` | Joins the same dependency solve and lock |
| Public [`@task`](/harnest/reference/api/task#task) | Uses built-in Harnest workers; provider dependencies come from project metadata |
| Active `mcp/*.py` | Adds the selected framework's MCP adapter |
| `serve`, `run`, or `test` | Selects the shared development profile |
| `test --evals` | Selects the Google ADK evaluation profile |

Harnest resolves the selected environment before importing the agent or its
Harnest Extensions. Production runtime, development, and eval use independent
locks so compiled deployment artifacts do not inherit development-only packages.

## Select compilation dependencies

Add `harnest-compile.yaml` beside your agent's `config.yaml` to select optional dependency groups:

```yaml harnest-compile.yaml
version: 1
extras: [crm]
```

Define the selected extra in the agent's configured `pyproject.toml`. Package versions stay in ordinary Python metadata:

```toml pyproject.toml
[project]
name = "sales-agent"
version = "1.0.0"
dependencies = ["httpx>=0.28,<1"]

[project.optional-dependencies]
crm = ["acme-crm-sdk>=2,<3"]
analytics = ["acme-analytics-sdk>=1,<2"]
```

Here, compilation selects `crm`; `analytics` is included only if another dependency requires it. These declarations affect `compile` and `runtime build --agent`, not development commands.

| Field | Behavior |
|---|---|
| `version` | Required; use `1`. |
| `extras` | Optional list of exact keys from the root project's `[project.optional-dependencies]`. Unknown extras fail the build. |

Compilation retains complete selected packages and their transitive dependencies. Use separate extras for optional integrations; Harnest does not trim packages based on observed imports.

### Project files and compiled content

Compilation includes Python, project configuration, dependencies, instructions, eval declarations, and complete installed skills, extensions, and plugins. Secrets, generated state, and virtual environments are excluded.

Teammate documentation and company authoring configuration stay in the project. Development commands still use the authored tree.

`harnest-compile.yaml` accepts only `version` and `extras`. A `resources` field is rejected, including an empty list. There is no general file-inclusion setting. Harnest does not infer arbitrary file reads from Python code.

Use agent templates for model-facing instructions and skills; copying a team guide into a project does not make it model-facing.

Selected optional dependencies use a separate `harnest-compile.lock` and environment. Refresh it with `harnest env sync AGENT_DIR --profile compile`. Native runtime packs retain their own resolution constrained by production locks.

[Project packs](/harnest/build/project-packs/create#declare-compilation-dependencies) can generate and migrate these declarations through their existing file and YAML operations. Pack authoring and migration tools stay in the authoring environment unless you explicitly declare them as runtime dependencies.

### Inspect a build report

| Output | Report location |
|---|---|
| Compiled directory | `OUTPUT/harnest-build-report.json` |
| Runtime pack | `PACK/harnest-build-report.json` |
| Native executable | `EXECUTABLE.build-report.json` beside the executable |

Build reports list selected dependencies, retained files, inclusion reasons, and sizes. Runtime reports add package versions, owners, and declared requirements; inactive markers remain metadata.

`logicalBytes` counts retained file bytes; `uniqueObjectBytes` counts distinct objects in that runtime. Neither includes filesystem overhead or measures savings across other packs. Package sizes can overlap.

Shared runtimes resolve the combined selected requirements of all listed agents. Identical files continue sharing the existing content-addressed store and launch cache. Changing selected requirements requires rebuilding runtime coverage; changing included agent content only requires recompiling the agent.

## Build native executables

Build executables for the deployment OS and architecture on a compatible baseline. The destination needs no Harnest or Python installation, but still needs your external services and credentials.

Choose how to ship the dependencies:

| Mode | Build command | Deployment |
|---|---|---|
| Attached runtime | `harnest compile ./sales --runtime ./dist/shared-runtime --output ./dist/sales-agent` | Ship the agent and its runtime pack separately. Several agents can attach the same pack. |
| Embedded runtime | Add `--embed-runtime` to the command above | Ship one executable containing the agent and runtime. |
| Automatic embedded runtime | `harnest compile ./sales --format executable --output ./dist/sales-agent` | Resolve a runtime for this agent and embed it automatically. |

On Windows, build on a Windows host and use an output filename ending in `.exe`. For example, in PowerShell:

```powershell
harnest runtime build --agent .\sales --agent .\support --output .\dist\shared-runtime
harnest compile .\sales --runtime .\dist\shared-runtime --output .\dist\sales-agent.exe
harnest compile .\support --runtime .\dist\shared-runtime --output .\dist\support-agent.exe
.\dist\sales-agent.exe --runtime .\dist\shared-runtime run "Help with my order"
```

Runtime packs target the build host; a Linux or macOS pack cannot be attached to a Windows executable. Packaged Python console tools remain usable after moving the deployment directory.

`--runtime` validates and references the pack. It does **not** copy dependencies into the agent executable unless you also pass `--embed-runtime`. Ordinary `compile` without these options still produces the existing Python artifact directory.

### Share dependencies across agents

Run these commands from the directory containing your agent folders:

```bash
harnest runtime build \
  --agent ./sales \
  --agent ./support \
  --output ./dist/shared-runtime

harnest compile ./sales \
  --runtime ./dist/shared-runtime \
  --output ./dist/sales-agent

harnest compile ./support \
  --runtime ./dist/shared-runtime \
  --output ./dist/support-agent
```

A shared pack resolves all agents’ dependencies together using current production locks as constraints. Sync stale locks first. Agents must use the same Python version; incompatible dependencies require separate packs.

Builds may download dependencies; launchers do not. Release CLIs include the launcher. Contributor builds require Go and can select a local wheel with `runtime build --wheel FILE`.

Keep build output outside the agent source, or under its `.harnest/` directory. Runtime output directories must be new: builds do not overwrite existing packs. When dependencies change, build a new pack and recompile the agents that should use it.

### Attach a runtime when launching

```bash
./dist/sales-agent --runtime ./dist/shared-runtime serve --port 8080
./dist/support-agent --runtime ./dist/shared-runtime run "Help with my order"
```

Place launcher options before `serve` or `run`. Relative paths resolve from the working directory. Set `HARNEST_AGENT_RUNTIME` instead of passing `--runtime` to every invocation. The launcher verifies the exact runtime digest and platform before loading agent code; a different pack is rejected even if it has a similar name.

The `run` command requires `spec.interfaces.cli: true` when the agent is compiled. It accepts a positional message or reads stdin when the message is omitted. Pass `run --help` or `serve --help` for command options.

Provide credentials through the deployment environment. Authored `spec.environment` values act as defaults; explicitly supplied environment variables take precedence. Use `--server-config FILE` before the command to replace the packaged server settings for one process. Keep durable state and deployment configuration outside the executable and runtime cache.

### Deduplicate dependency storage

Identical dependency files share storage across packs and the launch cache. Agents still run in separate processes.

By default, runtime builds use `.harnest-runtime-objects` beside the output directory. Use `runtime build --store DIRECTORY` to share one build store across other output locations. Packs contain their own object links and remain usable after the build store is removed; copy the complete runtime pack when deploying it. Hardlink-aware copying preserves sharing between multiple packs. Ordinary copies may duplicate their on-disk bytes until the launch cache deduplicates them.

Set `HARNEST_AGENT_CACHE` to override the user cache directory. Reused files are verified. Keep packs, object storage, and cache on one hardlink-capable filesystem for maximum sharing (one NTFS volume on Windows); otherwise Harnest copies files.

Embedding the same runtime into several executables necessarily repeats those bytes in the executable files. Use attached runtimes when distribution size matters. Embedded executables also materialize dependencies in the shared launch cache.

## CI

A minimal offline CI sequence is:

```bash
harnest env sync AGENT_DIR --profile development --frozen
harnest test AGENT_DIR
harnest env sync AGENT_DIR --frozen
harnest compile AGENT_DIR --output .harnest/my-agent
```

Add smoke or eval lanes only when CI has the required services and credentials. For Harnest source changes, follow [Development standards](/harnest/reference/development-standards).
