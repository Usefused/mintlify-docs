A **pack** bundles company scaffolding, typed settings, versioned migrations, commands, and Studio setup. Teams use it with `harnest init`, `harnest upgrade`, or `harnest studio` and `--pack DIR`, or through the pack's own command, such as `acme`.

Packs are authoring code. Their dependencies are not installed in deployed agents. Use a [Harnest Extension](/harnest/build/extensions) for capabilities that run inside the agent.

## What a pack contains

A pack is one folder:

```text
acme-pack/
  pack.yaml        # name, version, command, and the optional Studio sub-pack
  pack.py          # optional: init and migration hooks, company commands
  templates/       # optional: files your hooks copy into agents
  assets/          # optional: Studio UI files
```

| File | What it holds | Runs code? |
|---|---|---|
| `pack.yaml` | Identity, version ranges, the branded `command`, and an optional `studio:` sub-pack with builder defaults, UI, and installable resources. | No. Harnest and Studio read it as data. |
| `pack.py` | `pack = ProjectPack(schema_version=...)` with `@pack.initialize`, `@pack.migration`, and `@pack.command`. | Imported for project planning, pack validation, wheel building, and company commands. Studio catalog loading reads only the manifest and declared assets. |

## Try it

```bash
harnest pack init acme --output ./acme-pack
harnest init ./sales --pack ./acme-pack
harnest pack build ./acme-pack --output ./dist
```

The wheel installs the branded `acme` command for use as `acme init ./sales`.

## Supported decorators

Initialization and migration hooks are synchronous functions that return a [`ChangePlan`](/harnest/reference/api/authoring#changeplan). Harnest applies the proposed changes after planning succeeds.

| Decorator | Purpose | When it runs |
|---|---|---|
| [`@pack.initialize`](/harnest/build/project-packs/initialize) | Create company files and defaults. | When planning a new project, including a dry run. |
| [`@pack.migration(from_version=1, to_version=2)`](/harnest/build/project-packs/migrations) | Move an existing project to the next company schema. | When planning an upgrade that crosses that version. |
| [`@pack.command("check")`](/harnest/build/project-packs/cli#add-a-company-command) | Add a command to the pack's branded executable. | When someone runs `acme check`. |

Company command handlers receive argument strings and return an exit code; they execute immediately outside the project transaction. Harnest owns applying and recovering proposed changes.

## How changes reach the project

Harnest prepares its scaffold or core migrations in a temporary copy. Packs then propose their changes in the order you pass them. The planner validates company configuration and reports conflicts in one combined preview.
