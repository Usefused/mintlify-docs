A **pack** bundles company scaffolding, typed settings, versioned migrations, custom commands, coding-IDE skills, protected Python packages, pack-owned extensions, and Studio setup into a single branded CLI binary (such as `acme`). Teams can also test a pack folder directly with `harnest init`, `harnest upgrade`, or `harnest studio` and `--pack DIR`.

## What you can do with a pack

| What you want to ship | How to do it | Guide |
|---|---|---|
| Enforce company output policies or tool/model guardrails on every compiled agent | Add a pack-owned extension with `@lifecycle.output_policy` or invocation hooks under `extensions:` in `pack.yaml` | [Policies, plugins & bundles](/harnest/build/project-packs/capabilities#enforce-policies-with-pack-owned-extensions) |
| Auto-attach shared runtime tools, MCP servers, skills, or subagents without editing agent repos | Add a pack-owned extension under `extensions:` in `pack.yaml` | [Policies, plugins & bundles](/harnest/build/project-packs/capabilities#enforce-policies-with-pack-owned-extensions) |
| Attach a portable Agent Plugin (`plugin.json`, `mcp.json`, skills) to every new agent | Copy plugin files in `@pack.initialize` via `context.files.from_file` | [Attach an Agent Plugin](/harnest/build/project-packs/capabilities#attach-an-agent-plugin-to-every-agent) |
| Ship approved internal Python SDKs that agents cannot override | List PEP 508 requirements, local package folders, or `.whl` files under `packages:` in `pack.yaml` | [Protected Python packages](/harnest/build/project-packs/capabilities#protected-python-packages) |
| Distribute coding-IDE guidance (`<command> skills install`) | Declare `skills:` in `pack.yaml` (can override built-in skills) | [Coding-IDE skills](/harnest/build/project-packs/capabilities#coding-ide-skills) |
| Scaffold templates, company YAML config, and versioned migrations | Define `pack = ProjectPack(...)` hooks in `pack.py` | [Project hooks (`pack.py`)](/harnest/build/project-packs/hooks) |
| Customize Harnest Studio defaults, UI, and component catalog | Add a `studio:` section to `pack.yaml` | [Studio in your pack](/harnest/studio/packs) |

## What a pack contains

Only `pack.yaml` (required) and `pack.py` (optional) have fixed names. Everything else—templates, coding-IDE skills, local packages or `.whl` files, extensions, and Studio assets—can live in any subfolder inside the pack, as long as you point to its path in `pack.yaml` or `pack.py`:

```text
acme-pack/
  pack.yaml        # required: identity, command, and paths to skills/packages/extensions/studio
  pack.py          # optional: init and migration hooks, custom commands
  ...              # any subfolders you reference (templates, skills, sdks, extensions, assets)
```

| File | What it holds | Runs code? |
|---|---|---|
| `pack.yaml` | Identity, version ranges, branded `command`, coding-IDE `skills`, protected `packages`, auto-loaded `extensions`, and an optional `studio:` sub-pack with builder defaults, UI, and installable resources. | No. Harnest and Studio read it as data. |
| `pack.py` | `pack = ProjectPack(schema_version=...)` with `@pack.initialize`, `@pack.migration`, and `@pack.command`. | Imported for project planning, pack validation, pack building, and company commands. Studio catalog loading reads only the manifest and declared assets. |

## Try it

```bash
# 1. Scaffold a new pack folder
harnest pack init acme --output ./acme-pack

# 2. Validate and build the pack into a standalone branded CLI binary
harnest pack validate ./acme-pack
harnest pack build ./acme-pack --output ./dist

# 3. Use the branded binary to scaffold and compile an agent
./dist/acme init ./sales
./dist/acme compile ./sales --format executable --output ./dist/sales-agent
```

`harnest pack build` defaults to `--format binary`, producing a standalone `./dist/acme` executable that embeds Harnest and the pack so downstream teams do not need to install Harnest separately. Pass `--format wheel` to build the lightweight launcher wheel instead.

## Supported decorators

Initialization and migration hooks are synchronous functions that return a [`ChangePlan`](/harnest/reference/api/authoring#changeplan). Harnest applies the proposed changes after planning succeeds.

| Decorator | Purpose | When it runs |
|---|---|---|
| [`@pack.initialize`](/harnest/build/project-packs/initialize) | Create company files and defaults. | When planning a new project, including a dry run. |
| [`@pack.migration(from_version=1, to_version=2)`](/harnest/build/project-packs/migrations) | Move an existing project to the next company schema. | When planning an upgrade that crosses that version. |
| [`@pack.command("check")`](/harnest/build/project-packs/cli#add-a-company-command) | Add a command to the pack's branded executable. | When someone runs `acme check`. |

Company command handlers receive argument strings and return an exit code; they execute immediately outside the project transaction. Harnest owns applying and recovering proposed changes.

## How changes reach the project

Harnest prepares its scaffold or core migrations in a temporary copy. Packs then propose their changes in the order you pass them. The planner validates company configuration and reports conflicts in one combined preview.
