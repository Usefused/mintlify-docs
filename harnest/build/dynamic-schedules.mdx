Use dynamic schedules when users choose recurring work, such as a weekly report they can pause or reschedule. Harnest stores each schedule for the active user. For deployment-wide work owned by your application, use [Cron schedules](/harnest/build/scheduled-tasks).

See the [`harnest.cron` API reference](/harnest/reference/api/cron) for scheduling functions and [`CronJob`](/harnest/reference/api/cron#cronjob) methods.

## Setup

Register the same provider with [`@lifecycle.storage.tasks`](/harnest/reference/api/lifecycle#storage-tasks) and [`@lifecycle.storage.cron`](/harnest/reference/api/lifecycle#storage-cron) ([storage setup](/harnest/runtime/task-storage)) and keep `harnest serve .` running. Expressions use five cron fields in UTC. `harnest run` does not activate schedules.

## Functions and scheduled jobs

`cron/` contains schedulable functions. Each stored job supplies a user, timing, arguments, and status; many jobs can target one function. Use `cron.list()` to inspect the current user’s jobs.

## Create a schedule from a Tool

Declare the function once with `@cron()` in `cron/`, then select it by its filename without `.py`. Harnest creates its queued task automatically. No fixed schedule runs until managed code creates one:

<Steps>
<Step title="Declare recurring work">

```python cron/build_report.py
from harnest.cron import cron

@cron(queue="reports", max_retries=3)
async def build_report(account_id: str) -> dict:
    """Build one account report on the reports queue."""

    return {"account_id": account_id, "status": "ready"}
```

</Step>
<Step title="Create a schedule for the caller">

```python tools/schedule_report.py
from harnest import cron
from harnest.agent import tool

@tool
async def schedule_report(account_id: str, expression: str) -> dict:
    """Schedule a recurring UTC report for the current user."""

    job = await cron.create(
        key=f"weekly-report:{account_id}",
        expression=expression,
        task="build_report",
        arguments={"account_id": account_id},
    )
    return {
        "id": job.id,
        "expression": job.expression,
        "status": job.status,
        "timezone": job.timezone,
    }
```

</Step>
</Steps>

Names resolve to deployed `@cron` functions in the current application, including fixed schedules. Unknown targets or invalid arguments fail before storage.

Choose a stable `key` for the user's logical schedule. Repeating the same key and definition returns the existing job, even if paused or cancelled. Reusing the key with different settings conflicts; use [`update`](/harnest/reference/api/cron#update) when the user intends to change that schedule.

## Reuse an existing Task

Use `cron.create(task=existing_task, ...)` for registered [`@task`](/harnest/reference/api/task#task) work. Follow the [shared-library pattern](/harnest/build/queued-tasks#define-and-call-a-task) so the tool and task export share the same callable; separately imported or redecorated copies are rejected.

## Let users manage their schedules

Save the job ID to retrieve or change it later. [`cron.get()`](/harnest/reference/api/cron#get) and [`cron.list()`](/harnest/reference/api/cron#list) check the active user’s ownership on every call.

Use pause for a temporary break. Resume starts future runs at the next matching UTC minute. Use cancel when the schedule should stop permanently but you want to retain its record, or delete to remove it. See [`CronJob` methods](/harnest/reference/api/cron#cronjob) and [return behavior](/harnest/reference/api/cron#dynamic-schedule-behavior).

<Warning>
  Pausing, cancelling, or deleting a schedule affects future occurrences. It does not stop tasks already queued or running. Cancelled schedules cannot be updated or resumed.
</Warning>

## Ownership and execution caveats

Create and manage schedules inside a managed Harnest invocation with cron storage enabled. Standalone Python scripts and module imports do not have the active user and runtime required by these APIs.

Dynamic schedules run as their creating user with fresh context and empty grants. If the scheduled task invokes an agent that needs governed capabilities, configure an explicit [service principal](/harnest/runtime/agent-runtime-principals). Keep arguments free of credentials; resolve credentials when work executes.

Expressions use UTC, so explain the timezone to users and account for daylight-saving changes. Make task side effects idempotent because workers may retry. For validation failures and conflicting changes, see [Cron errors](/harnest/reference/api/cron#errors).
