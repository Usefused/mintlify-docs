A Harnest release bundles three matching parts: the native CLI, the Python runtime wheel, and `uv`. The installer verifies the release checksum before it changes your machine.

Harnest requires **Python 3.11 or newer**. New agents and the managed fallback runtime use Python 3.12.

## Install

<CodeGroup>

```bash Latest release
curl -fsSL \
  https://raw.githubusercontent.com/Usefused/harnest/main/install.sh |
  sh
```

```bash Non-interactive
curl -fsSL \
  https://raw.githubusercontent.com/Usefused/harnest/main/install.sh |
  HARNEST_YES=1 sh
```

```bash Pinned release
curl -fsSL \
  https://raw.githubusercontent.com/Usefused/harnest/main/install.sh |
  HARNEST_VERSION=v0.1.18 sh
```

```powershell Windows
$installer = Join-Path $env:TEMP 'install-harnest.ps1'
Invoke-WebRequest https://raw.githubusercontent.com/Usefused/harnest/main/install.ps1 -UseBasicParsing -OutFile $installer
powershell -NoProfile -File $installer
```

</CodeGroup>

The Windows command uses your existing execution policy. If the downloaded script is blocked, use the ZIP instructions below or ask your administrator to approve installation.

Verify the CLI and managed runtime:

```bash
harnest --version
harnest doctor
```

## Windows ZIP installation

Use this method when your device permits the Harnest executable but blocks downloaded PowerShell scripts. On managed devices, follow your organization's software approval process.

1. Open [Harnest releases](https://github.com/Usefused/harnest/releases/latest). Download `checksums.txt` and the ZIP for your Windows system type from the same release. Choose `harnest_<version>_windows_amd64.zip` for x64 or `harnest_<version>_windows_arm64.zip` for ARM64. Windows Settings → System → About lists your system type.
2. In PowerShell, calculate the archive hash, replacing the filename with the one you downloaded:

   ```powershell
   Get-FileHash -Algorithm SHA256 -LiteralPath "$HOME\Downloads\harnest_<version>_windows_amd64.zip"
   ```

   Compare the result with the entry for that exact filename in `checksums.txt`. Continue only if the full SHA-256 values match.
3. Extract the verified ZIP with File Explorer and place `harnest.exe` in a directory you own, such as `$HOME\.local\bin`.
4. Run these commands in PowerShell, using the directory you chose:

   ```powershell
   & "$HOME\.local\bin\harnest.exe" runtime install
   ```

   After installation succeeds, verify both layers:

   ```powershell
   & "$HOME\.local\bin\harnest.exe" --version
   & "$HOME\.local\bin\harnest.exe" doctor
   ```

5. Add the executable's directory to your user PATH in Windows Environment Variables and open a new terminal to use `harnest` directly.

## Diagnose an agent

From your agent folder:

```bash
harnest doctor .
```

`doctor` checks the configured framework and an existing managed environment without changing dependencies. Run `harnest env sync .` if the environment is missing or stale.

With no directory argument, `doctor` detects an agent in the current folder; otherwise it checks core packages only. `--framework adk` or `--framework langgraph` explicitly adds that framework's checks. `--python` and `HARNEST_PYTHON` select an explicit interpreter for diagnosis, and the output shows which interpreter was checked. A missing framework in the shared core runtime does not mean it is missing from an agent's isolated environment.

## Installer properties

| Property | Default | Use it for |
|---|---|---|
| `HARNEST_VERSION` | Latest GitHub release | Pinning a release |
| `HARNEST_REPO` | `Usefused/harnest` | Installing from a fork |
| `HARNEST_YES` | Unset | Explicit non-interactive approval |
| `HARNEST_INSTALL_DIR` | `$HOME/.local/bin` | Choosing the CLI destination |
| `HARNEST_RUNTIME_DIR` | `$HOME/.harnest/runtime` | Choosing the private managed runtime |
| `HARNEST_BOOTSTRAP_PYTHON` | Auto-detected | Requiring one exact host Python |
| `HARNEST_PYTHON` | Managed runtime | Overriding Python for later CLI commands |
| `GITHUB_TOKEN` | Unset | Reading a private fork's releases |

<Note>
  You run `harnest`; you do not activate the private runtime or call `python -m harnest.cli`.
</Note>

If no Python 3.11 or newer is available, embedded `uv` installs a pinned CPython 3.12 under the Harnest data directory. It does not modify the system Python.

## Upgrade

Run the installer again to replace the CLI and its matching managed runtime. Then upgrade each project separately:

```bash
harnest doctor
harnest upgrade path/to/agent
harnest upgrade path/to/agent --apply
harnest test path/to/agent
```

The first `upgrade` is a read-only plan. Apply handles supported source and Python-version migrations, verifies the planned source hashes, and writes backups before changing project files.

## Compatibility

Each release supports specified ADK and LangGraph versions. Sync resolves project and extension dependencies into separate hash-verified runtime, development, and evaluation locks.

| Check | Command |
|---|---|
| CLI and runtime match | `harnest doctor` |
| Project environment is current | `harnest env sync <project>` |
| Development environment is current | `harnest env sync <project> --profile development` |
| Source works with the selected framework | `harnest test <project>` |
| Artifact is reproducible | `harnest compile <project>` |

### Run examples from a source checkout

Keep the installed framework aligned with each example's committed `harnest.lock`. For the desktop MCP example, run this from the repository root after creating a Python 3.12 `.venv`:

```bash
uv pip install --python .venv/bin/python \
  --constraint examples/desktop-mcp-agent/framework-constraints.txt -e '.[adk]'
```

The example's provisioner uses the same pin when installing its extra dependencies, including when reusing an existing environment. Update the constraint and framework lock together when deliberately changing ADK versions.

## Publish a release

Release publishing is a maintainer workflow:

<Steps>
  <Step title="Run the complete gate">
    ```bash
    make quality
    ```
  </Step>
  <Step title="Prepare release notes and version metadata">
    Keep the native CLI, embedded wheel, and compatibility metadata on the same version.
  </Step>
  <Step title="Tag the release">
    The release workflow builds the supported macOS and Linux tarballs and Windows ZIP archives, creates `checksums.txt`, and publishes the artifacts.
  </Step>
  <Step title="Verify a clean install">
    Test the public installer and run `harnest doctor` on at least one supported platform.
  </Step>
</Steps>

<Warning>
  Do not publish a CLI with a wheel from another version. The executable rejects mismatched embedded metadata.
</Warning>
