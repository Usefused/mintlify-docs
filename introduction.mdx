Fused sits between the software making a call and the service being called. For every request it decides whether the call is allowed, resolves the credential, applies the policy, performs the provider interaction, and records what happened.

Your product code stops carrying provider auth, retries, and pagination. Your agents stop holding credentials. Both get one consistent way in.

## Create your first app

Use one command whether the caller will import a package, call the centralized API, or connect as an MCP client:

```bash
fused-cli init support-app --service linear
```

Without a mode flag, the terminal asks what you want to build. Pass a mode when you already know:

| Mode | Command shape | Successful result |
|---|---|---|
| Typed SDK | `fused-cli init <name> --sdk --service <service>` | Applied SDK config, downloaded package, and first-call guidance |
| Direct API | `fused-cli init <name> --api --service <service>` | Applied `kind: sdk` config with `generate: false` and a REST request template |
| MCP server | `fused-cli init <name> --mcp --service <service>` | Applied Engine-hosted server and its connection details |

Init generates only the desired-state files needed for the mode you chose. It does not add sample SDK or MCP configs that could be mistaken for resources you intended to apply.

## How a change reaches the Engine

Everything configurable is a file under `.fused/`, and every change is still governed by a plan and an apply.

```bash
fused-cli sdk plan     # validates and previews; may offer missing credential setup
fused-cli sdk apply    # commits exactly what the receipt describes
```

The receipt binds an apply to that exact file content and that exact Engine. If the file changes, or you point at a different Engine, the apply is refused rather than doing something you did not review. An unchanged apply is a no-op.

For a new app, `fused-cli init <name>` drives those boundaries for you. Choose a typed SDK, direct API, or MCP server, then select services and operations. The command can enable a missing service and create the app after one combined confirmation while retaining separate workspace and app receipts. Use the [advanced controlled workflow](/advanced/control-the-workflow) when you want independent review, structured CI output, or a recovery boundary.

In a terminal, omit interaction flags. Fused asks only when it needs a selection or confirmation, and SDK planning may offer optional credential setup. In automation, pass `--no-input` so missing required choices fail instead of waiting for a person; missing credential values remain non-blocking readiness metadata. Add `--json` when the command supports machine-readable output.

Immutable things behave accordingly: re-applying identical content to an existing app version changes nothing, and changing its scope returns `app_version_immutable`. You publish a new version instead of quietly rewriting the contract of software already in production.

## Three credentials

Keeping these apart avoids most early confusion.

| Credential | Authenticates | Lives in |
|---|---|---|
| CLI API key | Management calls to the Engine | Your CLI config, from `fused-cli login` |
| Execution token | An app or agent calling the Engine at runtime | Your application's secret manager |
| Provider credentials | The Engine to the provider | An Engine bucket |

Provider credentials never appear in a config file, a generated package, or an agent's context.
